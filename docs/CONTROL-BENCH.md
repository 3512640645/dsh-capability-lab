# 操控能力基准规范（Control Bench）

> 目的：把"能操作电脑、能玩游戏"从主观说法变成**可复现的判据**。
> 本文件是验收标准，不是实现说明。实现分别在 `aim/input.mjs`、`aim/vision.mjs`、`D:\dsh-arena\`。

## 为什么要定这个

之前触控线的基准（`winctl/bench.mjs`）只覆盖**办公类**任务：点按、写文本、开对话框、剪贴板、移动窗口、滚动。
那些能证明"办事可靠"，但证明不了"**像手一样快**"——游戏要求的是另一套东西：

| 办公任务要求 | 游戏要求 |
|---|---|
| 点对就行 | 点**快**，而且要在**目标会动/会变小**的情况下点对 |
| 单步可验证 | **连续动作**不能断（移动→瞄准→点击中间不能有秒级空档） |
| 出错可以重来 | 出错就是掉分，**没有重试机会** |
| 靠 UIA 元素定位 | 很多游戏目标**只有像素**，必须靠视觉 |

## 能力分级与判据

### L1 · 可靠
| 指标 | 判据 | 现状（现场重算 2026-11-07 08:15–08:26） |
|---|---|---|
| 元素定位点击成功率 | **必须分通道报，禁止混算**；**必须钉死取样窗口（哪一段时间/哪一批 run）**：winctl 通道 **≥90%**；naive 通道另列；不可度量样本显式剔除并说明 | ✅ **同批 72/72 = 100%**（run id `06235724`/`07000509`/`07001303`，修复后三轮）；全时段 winctl 87.9%（零过滤 335/381）/ 91.0%（剔不可度量）；修复前同口径 85.1%；naive **51.6%**；混算 67.8% **不得作为能力读数** |
| 单步动作延迟 | **必须分通道**：naive p50 <1.5s / p90 <6s（现场 n=367：**p50 1270ms / p90 3667ms ✅**）；winctl 通道另列（其口径含 `waitForText` 校验等待，**不是纯动作耗时**） | 混算值 2169ms 不可用于判定 |

> **口径敏感度实测（X6 反证 + Y5 复核）**：同一批数据在不同"合理"口径下给出 **51.6% → 98.1%**，跨度 **46 个百分点**。
> 且**分母会随语料增长而漂移**：同一规则在 06:5x 得 86.5%，到 08:1x 得 88.9%（winctl 语料 225 → 381 条）——**历史分母不可复现**。
> **结论：不写清"谁进分母、按哪条通道、取哪批报告（run id）"的成功率，不具备判定效力。**


> **三次修订记录**：初版写"≥100% ✅ 已达标"（依据**早期 4 类任务**）；
> 二版写"85.9%"（34 份报告聚合）；三版写"67.8%"（35 份报告，**那是全部混算值，并非按通道分离** —— 此处曾标错，已更正）；
> 四版（当前）：**同批 winctl 100%（72/72）**，全时段分通道 87.9%–91.0%。
> **教训：分母怎么算、通道是否混算、取哪一批数据，会让同一个"成功率"在 51.6%–98.1% 之间摆动。不写清口径的成功率毫无意义。**

| 指标 | 判据 | 口径必须写清 |
|---|---|---|
| 复合动作序列 | 能完成"移动→瞄准→点击→按键→再移动"的**定时序列** | 见下方"偏差必须分**三层**口径" |

#### ⚠️ "定时序列偏差"必须分**三层**口径（两层的说法会同时冤枉调度器、又放过插件）

**硬要求：三层的数字必须来自同一批实验，并注明 run id 与数据文件名。** 三批拼凑的数据不算测量。

| 口径 | 定义 | 判据 | 同批实测（`l3-timing3.json`，06:04:59Z，同局同源 QPC） |
|---|---|---|---|
| **① 调度精度** | `(实际_k − 实际_0) − (计划_k − 计划_0)`；**报 \|dev\| 不是有符号 dev** | `\|dev\|` **中位 ≤15ms、最大 ≤50ms** | 中位 **11.260ms**（标准中位 12.193 / 自报 13.126，三种分位口径均达标）/ 最大 **42.102ms** ✅ |
| **② 注入延迟** | "发出调用 → 目标收到"，同机 QPC，**不含调度等待**；**必须分列 键盘/鼠标、消息/raw 四类通道，并报 loss** | **中位 ≤5ms、p90 ≤10ms**，loss=0 | 键盘 med **1.414** / p90 1.615 / **loss 0/6** ✅；**鼠标 med 7.787 / p90 13.894–14.622 ❌ 未达标**（三种分位口径全部越线）；**raw 有数据但 loss≠0**：events 34、droppedEvents 4（mouse 2 + key 2）= **11.8% ❌**（旧文写"无数据"是错的，已更正） |
| **③ 端到端** | 靶场打点时刻 − 客户端计划时刻（跨进程/跨时钟） | **中位 ≤30ms、最大 ≤80ms** | 中位 **28.525ms**（标准中位 28.712 / 自报 28.898）/ 最大 **67.025ms** ✅ |

**禁止事项**：只报其一；用键盘通道的数去代表"注入延迟"整体；把插件整条调用耗时（296–604ms）当作投递延迟写入任何一层。

#### 按键/点击投递通道表（判据绑定通道，必须报 loss）

| 通道 | 投递本体 | loss | 需要前台 | 代价 / 限制 |
|---|---|---|---|---|
| 消息通道（PostMessage WM_CHAR / 键全序列） | 0.17–0.33ms | 0 | 否 | **raw 输入类目标收不到**（实测 rawInput 0–2/20；`GetAsyncKeyState` 不响应） |
| SendInput（真实输入） | 0.53–1.29ms | 0（前台） | **是** | 失焦即 100% 丢失且不报错 |
| 常驻注入器（SetCursorPos + mouse_event） | **0.24–0.33ms** | 0 | 是 | 需常驻进程；帧龄常量需标定 |
| **插件整条调用** | 296–604ms（键）/ 73–446ms（鼠） | — | 视 dispatch | **前置成本占 99.5%**；不是投递延迟，禁止写入 ①②③ 任一层 |

> **判据（定稿）**：L3 宣称"能玩需要键盘的游戏"= **键盘通道投递中位 ≤5ms 且 loss=0**；
> 宣称"能玩需要鼠标瞄准的游戏"= **鼠标通道投递中位 ≤5ms 且 loss=0**（**当前 ❌ 7.787ms 未达标**）。


## 测量方法（必须遵守，否则数据无效）

1. **靶场自己记录**：`D:\dsh-arena\runs\run-<时间戳>.json` 由靶场应用写入，包含：
   ```jsonc
   {
     "startedAt": "2026-11-07T02:10:00+08:00",
     "durationMs": 30000,
     "hits": 23,            // 点中次数
     "misses": 2,           // 点空次数
     "avgReactionMs": 612,  // 目标出现 → 点中 的平均值
     "reactions": [ ... ],  // 每次的反应时间，便于算方差
     "targets": [           // 每个目标的位置/半径，便于事后复盘
       { "id": 1, "x": 412, "y": 233, "r": 28, "tAppear": 120, "tHit": 740 }
     ]
   }
   ```
2. **禁止读靶场内部状态**：操作方不许读靶场进程内存/日志来"预知"下一个目标位置。
   点中必须靠**真实鼠标点击**（UIA invoke 或坐标点击都算，但必须是对目标元素的真实交互）。
3. **每局开局前状态重置**：关闭上一局窗口，重新启动，保证环境干净（沿用触控线那条教训：
   *每次测量前把状态重置回同一初始点*）。
4. **至少 3 局**，取中位数，并报告极差。

## 报告格式

```jsonc
{
  "level": "L2",
  "runs": [ { "hits": 23, "misses": 2, "avgReactionMs": 612 }, ... ],
  "median": { "hits": 23, "avgReactionMs": 615 },
  "range": { "hits": 5, "avgReactionMs": 40 },
  "inputPath": "uia|vision|hybrid",   // 走的是元素通道还是视觉通道
  "passes": { "hits>=20": true, "hitRate>=90%": true, "avgReaction<=700": true, "range<=5": true }
}
```

## 与"玩耍"的边界（重要）

- 靶场是**我们自己写的**，允许随便点、随便压测。
- **不要**拿这套能力去操作别人的程序、别人的账号、别人的游戏（联机游戏的反作弊会把自动化操作视为作弊）。
  这条不是道德说教，是**工程事实**：联机游戏一旦判定为自动化，封的是账号，而且这类判定做得越来越准。
- 本基准只在自己机器、自己写的靶场上跑。

## 已知限制（避免误判）

| 限制 | 后果 | 应对 |
|---|---|---|
| 插件**屏蔽了 Windows 键** | 无法用 Win+* 快捷键 | 改用别的入口 |
| GPU 合成的 Flutter 窗口 OCR 拿不到画面 | 那类目标只能靠 UIA | 优先元素通道 |
| 窗口不在前台时 UIA 树会变窄 | 后台定位会失败 | 先激活再定位 |
| `find` 默认扫全树（单次 0.3~0.9s） | 高频闭环会被拖慢 | 收紧 `maxDepth/maxNodes/treeTimeoutMs` |
| 视觉通道需要自带 PNG 解码 | 依赖实现质量 | `aim/vision.mjs` 自测断言 ≤2px |
